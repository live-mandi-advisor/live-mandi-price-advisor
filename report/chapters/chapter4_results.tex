\section{Database Schema Implementation}
The schema described in Chapter~3 was implemented using SQLAlchemy Core
against Supabase PostgreSQL: five normalized lookup tables
(\texttt{states}, \texttt{districts}, \texttt{markets},
\texttt{commodities}, \texttt{varieties}) respecting a strict hierarchy
(district scoped by state, market scoped by district, variety scoped by
commodity -- a market or variety name is not assumed unique on its own),
plus \texttt{price\_records} (the single fact table, not partitioned by
state), \texttt{forecasts}, and \texttt{model\_registry}. The connection
and schema creation were verified independently before any data loading
was attempted.

\section{Engineering Issue Encountered and Resolved}
The first full backfill run used a 5{,}000-row batch size for the
PostgreSQL upsert and failed partway through, most likely due to a
statement-size or connection-duration constraint on Supabase's free
tier (the exact server-side cause was not confirmed from the client
traceback). Because the entire backfill runs inside a single database
transaction, the partial run was safely rolled back rather than leaving
inconsistent data. Reducing the batch size to 1{,}000 rows resolved the
issue without any other pipeline changes, and the corrected run
completed successfully with the results above.

\section{Model Training and Evaluation}

\subsection{Training Setup}
One Prophet model was trained per eligible (commodity, market) pair.
Eligibility required at least 180 distinct reporting days of history,
applied within the 18 finalized (state, commodity) combinations only.
Varieties were averaged per (commodity, market, date) as described in
Section~\ref{sec:variety}. Training used all available history
(2024-01-01 to the pair's last reported date); joblib parallelism
(\texttt{n\_jobs=-1}) was used to train all 2{,}347 models in parallel.

\subsection{Baseline Comparison}
A naive moving-average baseline was trained alongside Prophet for each
pair. The baseline computes a 7-observation trailing mean of the training
series and carries it forward flat as the forecast. Both models were
evaluated on a rolling holdout using three non-overlapping 7-day
evaluation windows anchored to each pair's own last observation date,
with a minimum of 6 pooled actual observations required. Prophet was
selected for a pair only if its MAE was at least 5\% lower than the
baseline (i.e.\ $\text{MAE}_\text{Prophet} \leq 0.95 \times
\text{MAE}_\text{Naive}$).

\subsection{Interpretation}
The naive baseline's consistent outperformance is a known characteristic
of short-horizon agricultural price forecasting: mandi prices are noisy
and mean-reverting, which favors simple baselines over trend-sensitive
models. This result is itself a contribution -- it provides evidence that
Prophet adds limited value over a simple trailing average for most
commodity-mandi pairs in this dataset, with Snakeguard as the notable
exception (Prophet marginally better, 13.87\% vs.\ 14.11\% NMAE).

Tomato showed the worst Prophet performance (56.82\% NMAE vs.\ 6.98\%
for the baseline), consistent with its high short-term price volatility
making trend extrapolation unreliable.

For the working demonstration, Prophet forecasts are used for all pairs,
as the application's purpose is to demonstrate the full ML pipeline
rather than optimize per-commodity method selection. The baseline
comparison is documented here as an experimental finding.

\section{Forecast Generation and Sell/Hold Logic}
Forecasts were precomputed for all 2{,}347 active models using
\texttt{generate\_forecasts.py}, producing 17{,}451 rows in the
\texttt{forecasts} table (7 rows per model). The Sell/Hold signal is
computed by comparing the last-day forecast price against the last known
actual price: a forecast trending upward beyond a 2\% noise band
produces a HOLD signal (price expected to improve); flat or falling
produces a SELL signal. Across all pairs, 1{,}413 received SELL signals
and 1{,}080 received HOLD signals.

\section{Backend and Frontend}
The FastAPI backend exposes five endpoints: \texttt{GET /states},
\texttt{GET /states/\{state\}/top-crops}, \texttt{GET
/states/\{state\}/summary}, \texttt{GET /forecast}, \texttt{GET
/history}, and \texttt{GET /compare}. The React frontend provides a
two-page application: a Home page with project introduction and a
Prediction page with a four-step navigator (state $\to$ crop $\to$
market $\to$ forecast view). The forecast view offers both a full price
history chart (Jan 2024 to the market's last observation date, with the
7-day Prophet forecast and confidence band highlighted) and a tabular
view with SELL/HOLD badges. All forecasts display a prominent
``Historical demo -- Data as of 29 Dec 2025'' banner.

\section{Discussion}
The implementation validated several Chapter~3 design decisions against
real data: the hierarchical lookup-ID mapping was necessary in practice
(market and variety names recur across districts/commodities), the
variety-averaging decision resolved the multi-row problem cleanly, and
the 180-day minimum history threshold excluded approximately 54\% of
(commodity, market) pairs from Prophet training -- a reasonable
trade-off between coverage and model quality. The main finding from the
ML evaluation -- that the naive baseline outperforms Prophet on most
pairs -- is treated as an honest experimental result rather than a
failure, and is consistent with published findings on short-horizon
agricultural price forecasting.
