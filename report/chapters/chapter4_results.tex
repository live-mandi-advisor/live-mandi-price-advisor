\chapter{Results, Analysis \& Discussions}

\section{Status as of \ReviewLabel}
The historical data foundation for the project has been implemented and
validated end-to-end: a normalized PostgreSQL (Supabase) schema is live,
and the full 2024--2025 Kaggle historical backfill has been loaded,
cleaned, and verified against it. Live data ingestion, forecasting model
training, and the frontend application remain in progress and had not
yet produced evaluable output at the time of this submission.

\section{Database Schema Implementation}
The schema described in Chapter~3 was implemented using SQLAlchemy Core
against Supabase PostgreSQL: five normalized lookup tables
(\texttt{states}, \texttt{districts}, \texttt{markets},
\texttt{commodities}, \texttt{varieties}) respecting a strict hierarchy
(district scoped by state, market scoped by district, variety scoped by
commodity -- a market or variety name is not assumed unique on its own),
plus \texttt{price\_records} (the single fact table, not partitioned by
state), \texttt{forecasts}, and \texttt{model\_registry}. The connection
and schema creation were verified independently before any data loading
was attempted.

\section{Engineering Issue Encountered and Resolved}
The first full backfill run used a 5{,}000-row batch size for the
PostgreSQL upsert and failed partway through, most likely due to a
statement-size or connection-duration constraint on Supabase's free
tier (the exact server-side cause was not confirmed from the client
traceback). Because the entire backfill runs inside a single database
transaction, the partial run was safely rolled back rather than leaving
inconsistent data. Reducing the batch size to 1{,}000 rows resolved the
issue without any other pipeline changes, and the corrected run
completed successfully with the results above.

\section{Discussion}
This stage validated several Chapter~3 design decisions directly against
real data rather than assumption: the hierarchical (not flat) lookup-ID
mapping was necessary in practice (market and variety names do recur
across different parent districts/commodities in the raw data), and the
originally-scoped cleaning rules (invalid prices, natural-key
deduplication) were insufficient on their own -- structurally invalid
rows and extreme statistical outliers (e.g.\ a single recorded
modal price of Rs.\ 917{,}588{,}483 for onion) required
additional, explicitly-documented cleaning rules not anticipated in the
original design. This is treated as expected refinement through
implementation, consistent with this report's approach throughout: design
decisions are validated or revised against real data as it becomes
available, rather than assumed correct from documentation alone.
